2.2 架构特征

  • 纯静态零构建：无打包、无框架、无 CDN 依赖，一个目录丢到任意静态托管即可运行 —— 这是最大的工程优势，也直接降低了上线与维护成本。
  • 全局脚本共享：16 个脚本按顺序加载，162 个顶层函数 + 62 个顶层变量全部挂在 window 上，靠命名约定避免冲突（已核实当前无重名）。
  • 数据全本地：8 个 localStorage 键（workStatusMap / countdownList / todoList / todoReminderLog / schedulePlan / calendar_theme / weatherCache / weatherLocation），零后端、零账号。
  • 三处外部依赖：open-meteo 天气、open-meteo 地理编码、bigdatacloud 坐标反查 —— 均为免费免 key 服务。

三代码复审

3.1 值得肯定的部分

  • 防御式数据清洗做得标准：sanitizeStatusMap()、sanitizePlanData()、isValidTodo() 三层校验，导入的脏数据（非法日期键、越界数字、超量条目）一律挡在 localStorage 之外。这类细节在同规模个人项目里很少见。
  • 异常保护覆盖到位：所有 setItem 都包了 try/catch，隐私模式 / 配额满时静默降级并提示，不会白屏。
  • 时区处理正确：parseDateOnly() 手动拆解日期而非 new Date('YYYY-MM-DD')，规避了 UTC 偏移导致「差一天」的经典坑；getDaysInMonth() 用 new Date(y, m, 0) 取月末，写法地道。
  • XSS 防护意识到位：所有用户输入（待办标题/详情、方案名、城市名）一律走 textContent，未发现把用户数据拼进 innerHTML 的地方。
  • 撤销/重做设计克制：只记录「变更差异」而非全量快照，批量操作合并为一条历史，内存占用小、撤销粒度符合直觉。
  • 农历方案选型正确：放弃查表改用天文算法库，一次性解决跨年误差与节气错算（历史上曾错 14 处节气、缺 47 天）。
  • PWA 缓存策略成熟：HTML 走 network-first（在线永远拿最新版）、静态资源走 cache-first + 后台更新，版本号升版流程已成文。这是踩过「线上丢样式」事故后沉淀的正确做法。

3.3 已核实的「伪问题」（避免误判）

① storage.js 加载顺序在 history.js 之前，却调用 applyChanges() —— 会报错吗？
不会。applyChanges 是函数声明（存在提升），且只在用户操作时被调用，那时 history.js 早已加载完成。属于隐式耦合而非 bug，但建议补一行注释说明依赖。

② 农历 300 KB 库会不会拖慢首屏？
影响可控。它以 defer 加载且不阻塞 DOM 渲染，并已进 SW 预缓存（第二次访问零网络）。真正的代价是首次加载流量与小程序包体积（详见第六章）。

③ 「线上与本地不一致」是不是又发生了？
本次复审文件哈希与线上一致，无此问题。历史上该现象的唯一根因是 Service Worker 旧缓存，现已通过 CACHE_NAME 升版规范（当前 v9）规避。

六微信小程序移植评估

核心结论（请先接受这个前提）：小程序不是「移植」，而是「复用逻辑、重写界面」。 当前项目的界面完全建立在 document.createElement + innerHTML + 内联样式之上， 而小程序是 WXML 模板 + setData 数据驱动，没有 DOM。所有视图代码必须重写。 可复用的是「不碰 DOM 的纯逻辑」，约占代码量的 40–50%。

6.2 六大难点与对策

① 视图层整体重写（最大的工作量）

Web 端 6 个渲染文件（calendar / countdown / todo / todo-reminder / weather-location / plan）全部依赖 DOM API。小程序需改为「data 驱动 + WXML 循环渲染」。对策：优先重写核心的日历视图与侧栏；弹窗可先用小程序原生组件过渡。

② 农历库 300 KB 包体压力

小程序主包上限 2 MB，整个项目打包后必须严格控制。对策：把农历计算放入分包按需加载；或只抽取「农历日期 + 节气」所需算法（lunar-javascript 可按需裁剪）；也可在构建时预生成 10 年数据表（代价是跨年需更新，与你当初否决查表方案的理由冲突，需权衡）。

③ request 合法域名 —— 最硬的坎

小程序只能请求在后台白名单配置过的 HTTPS 域名，且通常要求域名已备案。而当前三个数据源（api.open-meteo.com、geocoding-api.open-meteo.com、api.bigdatacloud.net）均为境外域名，配置后国内访问稳定性无法保证。对策：自建一层轻量代理（这也意味着引入后端/云函数，项目将不再是「零后端」）；或改用国内天气服务商（需 key 与配额管理）。

④ 定位权限与隐私合规更严

需在 app.json 声明 requiredPrivateInfos: ["getLocation"]，配置「用户隐私保护指引」，并在首次调用前弹自己的授权说明。对策：把 Web 端已有的「定位说明卡」文案直接复用为小程序的自定义授权弹窗，这套合规思路可平移。

⑤ 数据无法从 Web 平移

localStorage 与小程序 Storage 完全隔离，老用户无法自动带数据过去。对策：恰好 Web 端的导出 JSON（version: 4）是标准格式 —— 让小程序实现「导入同一份 JSON」即可完成迁移，导入导出协议天然复用。

⑥ 无云同步，跨设备体验落差

小程序用户对「换手机数据还在」有天然预期。对策：配微信云开发（CloudBase）做云端备份，成本低、免运维，还能顺带获得用户体系。

C. Web 优先 先做 Web 上线验证需求，小程序后置 成本最低、见效最快；用真实用户数据决定是否值得投入 暂时放弃小程序流量入口 强烈推荐
无论走哪条路，都建议先做一件事：把与视图无关的「核心逻辑层」抽成一组无 DOM 依赖的纯 JS 模块 （日期工具、农历封装、进度计算、方案求值、数据清洗、排序规则）。 这样 Web 与小程序可共享同一份逻辑，也是将来无论走 A 还是 B 都受益的前置投资。

6.5 审核与合规提示

  • 类目：选「工具 - 效率」通常最顺；排班日历属工具类，无内容风险。
  • 定位类目：调用 getLocation 需在「小程序管理后台 → 开发设置 → 接口设置」申请，并填写用途说明（「用于获取所在城市天气」）—— 与 Web 端说明卡口径一致即可。
  • 隐私协议：必须在后台配置《用户隐私保护指引》，勾选「位置信息」「设备信息」，否则新版本无法提交。
  • 无支付、无 UGC、无社交：大幅降低审核复杂度，通常 1–3 个工作日可过。

8.1 数据兼容性（好消息）

现有导出格式 { version: 4, statuses, countdowns, todos, plan, theme } 是平台无关的标准 JSON。 这意味着：Web ↔ 小程序的数据迁移可以零成本打通 —— 小程序只需实现「导入/导出同一份 JSON」， 用户即可把 Web 上积累的排班数据无缝带进小程序。这是当前架构里最有价值的一处前瞻性设计。

8.3 一句话总结

代码本身没有拦路虎，产品化还差临门几脚，小程序是一场需要重新起跳的跳远。
建议：先用 3–5 天把 Web 打磨到「可公开发布」，3 天做逻辑层解耦，3–5 天补数据韧性； 小程序的 4–6 周投入，留给「Web 端已被真实用户验证」之后再决定 —— 届时你现在已具备的一整套纯净逻辑与标准数据格式，会让那次重写省下大量返工。
